# aura: project guide

Mobile-first web app that helps friend groups find and meet other friend groups (Team Aura class project). See README.md for setup and the vertical-slice demo.

Machine-specific notes (paths, accounts, local setup) belong in `CLAUDE.local.md`, which is git-ignored. Never put them here.

## Stack
- `client/`: React 19 + Vite 7, plain CSS (`client/src/styles.css` holds the design tokens). Hash routes: `#/find`, `#/messages`, `#/messages/:chatId`, `#/profile`, and the admin portal `#/admin`, `#/admin/users`, `#/admin/interests`, `#/admin/meetups`, `#/admin/groups`, `#/admin/groups/:id`, `#/admin/records`, `#/admin/tables/:name`, `#/admin/okrs` (`screens/AdminPortal.jsx`, Maintain Users / Interests / Meetups / Groups in `screens/AdminUsers.jsx`, `AdminInterests.jsx`, `AdminMeetups.jsx`, `AdminGroups.jsx`; outside the app's sign-in and the onboarding gate; signed out it's the landing page with the admin sign-in form). There is no Map tab; it's out of scope.
- `server/`: Node + Express 5 REST API. It talks to Postgres with `pg` only. Don't add the Supabase JS client.
- `db/`: `schema.sql` (drops and recreates everything) and `seed.sql` (truncates, then inserts demo data).
- `docs/`: ERD as `erd.dbml`, `erd.mmd` and `erd.png` (`npx @mermaid-js/mermaid-cli@12.2.0 -i docs/erd.mmd -o docs/erd.png --size 4800`, which reproduces the committed image's look and size).
- CI: `.github/workflows/ci.yml` runs `npm ci && npm run build` on every PR; merge only through PRs (README "How We Merge").
- Hosting: Render, from `render.yaml` (API web service + static client). The client reads `VITE_API_URL` at build time; the API allows only `CORS_ORIGIN`. The static site also rewrites `/api/*` to the API (`routes` in `render.yaml`): the admin portal always calls its own site's `/api` so its session cookie is first-party (Safari drops cookies between the two `onrender.com` sites). Pushing to `main` redeploys.
- Database: the shared Supabase project **Find Friends App**, reached through the Session pooler (port 5432). The connection string lives only in `server/.env`.
- Profile photos: Supabase Storage, public bucket `profile-photos`, called over its REST API with `fetch` in `server/src/lib/storage.js` (still no Supabase JS client). Needs `SUPABASE_SERVICE_ROLE_KEY` (plus the `SUPABASE_URL` sign-in already uses) in `server/.env` and on Render; the service_role key never goes to the client.
- AI: the API calls Google's Gemini API to write 3 conversation starters for each new match. `server/src/lib/gemini.js` is the only file that talks to it (plain `fetch`, no SDK); `server/src/lib/suggestions.js` has the prompt, the checks on the answer and the `chat_suggestions` queries. The key is `GEMINI_API_KEY`, read from the API's environment (Render's Environment tab, or `server/.env`); `GEMINI_MODEL` overrides the model.

## Commands (run from the repo root)
- `npm install`: installs both workspaces.
- `npm run dev`: starts the API (`API_PORT`, default 4000) and Vite (5173, which proxies `/api` to the API).
- `npm run db:check`: connects with `server/.env` and prints the `users` row count. It's read-only.
- `npm run db:reset`: runs schema then seed. **This wipes the shared team database.** Ask the team (or the user) before running it.
- `npm run db:demo-accounts`: creates a demo login (Supabase Auth, `<first name>@example.com`) for each of the 16 seeded users and links it. It needs `DEMO_PASSWORD` in `server/.env`, and it's safe to re-run; run it again after `db:reset`, which unlinks them. The `auth.users` foreign key can only be added by the `postgres` login, so `schema.sql` and migration 003 skip it with a warning when run as `aura_app`.
- `npm run db:migrate`: runs every `db/migrations/*.sql` (re-runnable) and prints the OKR percentages. It keeps everyone's data except what a migration deliberately removes (002 drops the old events tables).
- The `verify:*` scripts sign in as the demo accounts (`server/scripts/lib/session.js`), so they need `SUPABASE_PUBLISHABLE_KEY` and `DEMO_PASSWORD` in `server/.env`.
- `npm run verify:slice`: end-to-end check of the Accept flow. It mutates data, so follow it with `db:reset` only if the team agrees.
- `npm run verify:chat`: end-to-end check of live chat updates (`?after=` polling, list re-sort). It posts a real message and marks a chat read, so ask the team before running it on the shared database, and follow it with `db:reset` only if the team agrees.
- `npm run db:admin-account`: creates an admin portal login from `ADMIN_EMAIL` / `ADMIN_PASSWORD` in `server/.env` (or `-- <email>`), saving only a bcrypt hash; re-running changes the password and ends that admin's sessions. Run it again after `db:reset`, which deletes admin accounts.
- `npm run verify:admin`: end-to-end check of the admin sign-in (401 without a session, wrong password, lockout, cookie flags, only hashes stored, log out). Needs `ADMIN_EMAIL` / `ADMIN_PASSWORD` for an existing admin; it adds and removes one `admin_sessions` row, so it's fine on the shared database.
- `npm run verify:admin-groups`: end-to-end check of Maintain Groups (401s, create, up to 10 members then `409 GROUP_FULL`, edit, owner hand-over, `409 LAST_MEMBER`, delete). It creates two test groups and briefly adds 11 existing users, then deletes them, so ask the team before running it on the shared database.
- `npm run verify:admin-users`: end-to-end check of Maintain Users (401s, every validation problem named at once with nothing saved, add / edit / delete, delete handling the person's groups). It adds and then deletes test people and groups, so ask the team before running it on the shared database.
- `npm run verify:admin-interests` / `verify:admin-meetups`: end-to-end checks of Maintain Interests (leaves the data as it was) and Maintain Meetups (needs a match with no meetup; KR4 rises for a few seconds, so ask the team first on the shared database). Both use `server/scripts/lib/admin-client.js`.
- `npm run verify:messages`: checks that bad messages (empty, whitespace or invisible only, `\u0000`, too long, not text) get `400 VALIDATION_ERROR` and save nothing. It's read-only and safe on the shared database; `-- --post` also saves two test messages.
- `npm run verify:receipts`: end-to-end check of read receipts. It posts a real message and marks a chat read for two people, so the same rules as `verify:chat` apply on the shared database.
- `npm run verify:typing`: end-to-end check of the typing indicator (ping, poll, clear, 5s expiry, 403/404). It posts one real message and marks a chat read, so the same rules as `verify:chat` apply on the shared database.
- `npm run verify:own-groups`: checks that Find and "Groups that liked you" never offer a person their own group. Leaves the data as it was.
- `npm run verify:custom-interests`: end-to-end check of custom interests (on the profile at once, not in the picker, one interest for every capitalization and spacing, in the picker at 10 people, bad names refused). It signs in as demo accounts 1-11 and adds a test interest to their profiles, then puts their interests back and deletes it; it's briefly in everyone's picker, so ask the team before running it on the shared database.
- `npm run verify:suggestions`: end-to-end check of the AI conversation starters (Accept doesn't wait for the AI, 3 rows saved, `used_at` on send, none once both groups have chatted; the fallback if the API has no key). It accepts a real request and posts two messages, so the same rules as `verify:slice` apply on the shared database. `-- --ai` only asks the AI for starters and prints them: it saves nothing and needs no demo login, so it's safe on the shared database, but it needs `GEMINI_API_KEY` in `server/.env` and uses one Gemini request.
- `npm run build`: production build of the client.

## Conventions
- Admin forms (Maintain Users) report every bad field at once: `400 VALIDATION_ERROR` with `details.fields = { field: message }`, shown under each field. Maintain Users edits only the `users` row (the aura profile), never Supabase Auth logins.
- API errors are always `{ error: { code, message, details? } }` with codes like `GROUP_FULL`, `NO_GROUP`, `NOT_ACTIVE_GROUP`. Database trigger errors (`AU001`, `AU002`) are mapped in `server/src/errors.js`.
- Auth is Supabase Auth (email + password). The client (`client/src/supabase.js`, `@supabase/auth-js` only) sends `Authorization: Bearer <access token>`. `authenticate` in `server/src/middleware/auth.js` verifies it against Supabase's public keys (`SUPABASE_URL`) and returns `401` otherwise. `identify` then loads the `users` row by `auth_user_id` (`403 NO_PROFILE` if none). Only `/api/health`, `/api/interests` and the admin login/logout/session routes are public (`POST /api/admin/session/app` needs the app's session). Don't bring back an `X-User-Id` path or a public user list.
- The admin portal has its own sign-in, not Supabase: `admin_users` (`user_email`, bcrypt `user_password`) and the httpOnly, `SameSite=Strict` cookie `aura_admin`, whose token is stored only as a SHA-256 hash in `admin_sessions` (`server/src/lib/adminAuth.js`). `routes/admin.js` is mounted before `authenticate`; every `/api/admin` route except login, logout and session runs `requireAdminSession` (`401 ADMIN_SIGNED_OUT`). The client calls it only through `client/src/adminApi.js` (same-origin `/api`; a Bearer token only for `POST /admin/session/app`). Never return `admin_users` or `admin_sessions` rows from the API.
- App admins (`users.is_admin`) sign in to the portal from the app with no password: `POST /api/admin/session/app` checks their Supabase session and `is_admin` (`403 NOT_ADMIN` otherwise) and makes their `admin_users` login (their app email, random unusable password) the first time. After a portal Log out, the portal doesn't sign them back in for that tab (sessionStorage `aura.adminNoAutoSignIn`) and offers "Continue as" instead. `npm run verify:admin-app-login` checks it.
- Find has labeled **Pass** / **Connect** buttons and the whole card must fit above them on a 390px phone (keep it short: 3 interests + "+N", one members row); swiping the card (`components/SwipeCard.jsx`, touch only) is just a shortcut. The first visit opens `components/FindExplainer.jsx` once per browser (`localStorage` `aura.findExplainerSeen`). Keep copy clear that Connect is for the active group and doesn't mean joining the other group.
- Find, likes, the incoming-likes inbox and the chat list always act as the user's **active group** (`actingGroupId` in `server/src/middleware/auth.js`).
- Group membership changes go through `createGroup`, `addMember`, `removeMembership` and `setOwner` in `server/src/lib/groups.js`, used by both the app (`routes/groups.js`) and Maintain Groups (`routes/adminGroups.js`). Don't write membership SQL anywhere else: these keep match chats, owners and active groups in step.
- Anything that has to be atomic goes through `withTransaction` (`server/src/db.js`), for example `recordDecision` in `server/src/lib/matching.js`.
- The JSON the API returns is camelCase; database columns are snake_case.
- UI: inline stroke SVG icons (`components/Icon.jsx`), no emoji, avatars: a person's main photo (`user_photos.position = 1`, sent as `photoUrl`) or, without one, their illustrated DiceBear avatar (`Avatar src={p.photoUrl} personId={p.id}`; `client/src/illustrated.js`), with `alt=""` because the name is always beside it; groups use initials on pastel, touch targets of at least 44px. Every real photo gets alt text naming the person; placeholders use `role="img"` with an `aria-label` instead of reading "[Photo 1]". Long names must wrap (`overflow-wrap: anywhere`) or shorten with an ellipsis, never overflow.
- Loading states come from `components/Loading.jsx`: `Skeleton` rows built from the real rows' classes where the layout is known, otherwise `Loader` (spinner and label). Mark the loading area `aria-busy="true"` and pair skeletons with a `LoadingStatus` (`role="status"`). The global `prefers-reduced-motion` rule in `styles.css` stops every animation.
- Layout: below 1024px wide it's the phone layout (430px column, bottom tab bar). At 1024px and up, `App.jsx` (`useMediaQuery`) switches to the desktop layout: a sidebar (`SideNav`), Messages as list + chat panes, Find card side by side, and Profile in two columns. All desktop CSS lives in the `min-width: 1024px` blocks at the end of `styles.css`. Keep phone styles outside those blocks.
- Schema changes go in `db/schema.sql` (and the ERD files), never only by hand in the Supabase dashboard. To change the live shared database without wiping it, also add a re-runnable file in `db/migrations/` and run `npm run db:migrate`.
- OKRs (KR1-KR4) come from the `okr_metrics` view; README "OKR Metrics" says which table each one reads. Never store or cache a KR number: the admin portal's OKR Dashboard (`#/admin/okrs`) reads them live from `GET /api/admin/okrs` (`server/src/routes/admin.js`), which needs an admin session. The only fixed numbers are the KR targets (`TARGETS` in `admin.js`). Admin accounts are made by hand with `npm run db:admin-account`, never by a migration or the seed. `users.is_admin` (set in the SQL Editor) shows an app user the Admin portal link and lets them sign in to the portal from the app.
- AI calls never run inside a request or a transaction, and nothing may depend on one succeeding: `queueSuggestions` starts the call after the match is committed and returns at once, and every failure (no key, timeout, bad answer) just means no openers. Whatever the model returns is checked (`readStarters`) before it's saved or shown. Send it group-level data only (names, cities, interests), never member names or messages.

## Business rules (enforced on the server or in the database)
- A Friend Group has at most 10 members (trigger `group_member_cap`, which raises `GROUP_FULL`). A chat has at most 30 people (`chat_participant_cap`, which raises `CHAT_FULL`).
- Only a group's owner can change its photo (`PUT`/`DELETE /groups/:id/photo`, `friend_groups.photo_url`) or remove members. When the owner leaves, the longest-standing member becomes the owner; the last member leaving deletes the group.
- Invite codes are 4-12 letters and numbers; `POST /groups/join` ignores spaces, dashes and case (`400 INVALID_INVITE_CODE`, `404 INVITE_NOT_FOUND`).
- A person has 1 main photo (position 1) + up to 3 more (positions 2-4). The first photo becomes main; `POST /me/photos/:id/main` swaps; deleting closes the gap.
- A group always has one owner and at least one member: the app deletes a group when its last member leaves, and Maintain Groups refuses to remove the last member (`409 LAST_MEMBER`). Removing the owner makes the longest-standing member the owner.
- A user can be in several groups but has one active group, which must be one of their own groups (composite FK `users_active_group_is_membership`).
- A group's shared interests are the union of its members' interests, computed by the `group_shared_interests` view and never stored.
- Custom interests: a name someone types that isn't an interest yet goes on their profile at once with `interests.in_picker = false`, so the interest picker (`GET /api/interests`, `in_picker` only) doesn't offer it. When 10 people (`PICKER_THRESHOLD`) have it, it joins the picker for good. Starter and admin-made interests are in the picker; an admin can add a custom one early (`PATCH /api/admin/interests/:id { inPicker: true }`), and only deleting takes one out. Names match without regard to case or spacing: they're stored tidy (`interests_name_tidy`) and unique on `lower(name)`. All interest writes from the app go through `readInterestNames` / `replaceInterests` in `server/src/lib/interests.js`.
- Two groups match when each group has a `connect` row in `group_likes` toward the other. The match, its chat and all members of both groups as participants are created in one transaction.
- Recommendations are ranked by shared interests, then 1st-degree mutual friends, then 2nd-degree, then same city, then distance. They exclude your own groups and any group the active group has already liked, passed on or matched with. "Groups that liked you" also hides requests from any other group the viewer is in (they couldn't answer them: `OWN_GROUP`).
- Onboarding gate: the app is unusable without a group (`403 NO_GROUP`). Creating or joining a group requires a complete profile (`403 PROFILE_INCOMPLETE`).
- A new match's chat gets 3 AI conversation starters in `chat_suggestions` (or none if the AI call fails). The chat offers the unused ones (`used_at IS NULL`) to both groups until someone from each group has sent a message, the same "both groups have talked" as KR3. Sending a message with `suggestionId` sets that row's `used_at`.
- Maintain Meetups (admin) keeps the same one-per-match rule (match row locked, `409 MEETUP_EXISTS`); its day is saved at noon UTC so the chat shows the picked day.
- "We met up!" (KR4): anyone in a match chat can confirm a meetup (`POST /chats/:id/meetup`). A match has at most one `meetups` row: the insert locks the match row and skips if one exists (`201` new, `200` already there). Chat responses carry `meetup: { metAt, confirmedBy } | null`.

## Secrets
- Never commit `server/.env`, real passwords (`DEMO_PASSWORD`, `ADMIN_PASSWORD`), full connection strings or API keys (`GEMINI_API_KEY`). `server/.env.example` only has placeholders. Never log a key or put it in a URL.
- `.claude/` (local Claude Code settings) and `CLAUDE.local.md` are git-ignored.
